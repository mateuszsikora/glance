# Architecture

Glance is a single-module native Android application written in Kotlin. It supports Android 8.0 (API 26) and newer, compiles against API 37, targets API 34, and is designed for long-running wall-mounted tablets.

## Runtime components

- `MainActivity` owns the fullscreen UI, scheduled dashboard selection, dashboard pager, idle-screen overlay and timer, settings gesture, brightness controller, reversible soft-off overlay, and communication with the background services.
- `ContentSchedulePolicy` resolves the active profile from the local day and time, falling back to the most recent earlier day, while `IdleTimeoutTracker` keeps elapsed-time inactivity calculations independent from wall-clock changes.
- `DashboardPagerAdapter` and `WebViewFragment` create one WebView page per configured dashboard. `DashboardOrigin` restricts top-level navigation to the dashboard origin and explicitly allowed login origins.
- `KioskService` is the foreground control plane. It owns MQTT, the optional remote configuration server, screen commands, schedule state, the nightly maintenance restart, and relaunch behavior independently of the Activity lifecycle.
- `WatchdogService` schedules health checks, periodic reloads, and memory-pressure recovery while avoiding unnecessary WebView work when the screen is off. `MemoryTrimPolicy` ignores every device-wide `TRIM_MEMORY_RUNNING_*` signal, including `RUNNING_CRITICAL`. On a 3 GB Huawei tablet that level arrived 33-74 times a day, mostly after charger connections, and none of the 80 dashboard reloads it caused over 62 hours lowered the native heap; the heap that grows sits in the GPU driver (step 9 under Data flow), where a reload cannot reach it. `TRIM_MEMORY_MODERATE` and above, a nearly full heap, and the system low-memory flag still reload (`IdleMaintenanceReload` under Data flow keeps such reloads off idle playback). The Activity's `WebViewReachabilityChecker` uses `DashboardReachabilityProbe` and `StaleDashboardPolicy` to recover individual pages that stayed loaded while their live connection died.
- `ScheduleManager` and `ScheduleReceiver` calculate and deliver daily screen transitions and the nightly maintenance alarm, whose time and on-screen conditions come from `NightlyMaintenancePolicy`. `AppRestarter` restarts the app process and relaunches the dashboard; `TabletRebooter` reboots the tablet instead on the nights a scheduled reboot is due. The idle WebView is drawn without a layer (`LAYER_TYPE_NONE`), which avoids a full-screen offscreen texture and an extra compositing pass in every frame of an all-day slideshow. `BootReceiver` restores the kiosk and reschedules work after boot, package replacement, clock, time-zone, and exact-alarm permission changes.
- `ScreenController` implements screen state changes. Device Owner mode can use `lockNow()`; regular-app mode uses a reversible black overlay and window brightness. `PowerWakePolicy` decides whether a display wake that followed a charger event has to be undone.
- `BatteryMonitor` and `BatteryReading` translate the platform's battery broadcast into the charge level and charging state published over MQTT, filtering the many events that change neither.
- `BrightnessController` maps ambient-light readings or remote brightness commands to the Android window.
- `DiagnosticLog`, reached through `Diagnostics`, is an opt-in journal of reload causes, idle-screen changes, page failures, charger and display events, and `MemorySample` lines (system memory, swap, app footprint). It writes on its own thread to two bounded files in private storage and writes nothing while disabled. Its switch lives in `DiagnosticSettings`, a separate preferences file, so `AppConfig` stays byte-identical for recovery builds; `MaintenanceSettings` follows the same rule. The WebView renderer is an isolated process an app cannot measure, so its growth appears as falling available memory and rising swap.
- `MemoryTrendMonitor`, fed by `WatchdogService` every 5 minutes whether or not the journal is on, keeps a day of native-heap samples in memory. `MemoryTrend` judges them from hourly minimums after a one-hour warm-up and suggests a restart interval; the latest verdict is stored in its own preferences file, the Memory section shows it, and the remote panel warns while it says the heap keeps growing. Nothing restarts on its account. `AppRestarter` asks for a verdict before a planned restart, which would otherwise lose the day's samples.
- `AppConfig` stores configuration and lifecycle state in private `SharedPreferences`. `SecretStore` encrypts the MQTT password using AES-GCM with a non-exportable Android Keystore key.
- `SettingsActivity` validates and applies user configuration behind a salted PBKDF2 PIN verifier with retry lockout.
- `RemoteConfigServer` exposes an opt-in, LAN-only HTTP form on port 8080. It shares `AppConfig`, validation, PIN lockout and the service reload path with on-device settings.
- `UpdateChecker` polls an operator-supplied manifest from the watchdog's timers. `UpdateManifestParser` and `UpdatePolicy` hold the pure parsing and decision logic; `UpdateInstaller` verifies the APK's signing certificate against the running installation and installs it through `PackageInstaller` using Device Owner privileges.

## Data flow

1. `GlanceApp` creates the shared configuration and notification channels.
2. `MainActivity` resolves the current content profile, renders its dashboard URLs, and starts both foreground services unless kiosk mode was deliberately suspended. The first dashboard WebView of a process waits for `ColdStartGate`. Creating it starts Chromium on the main thread, and on a 3 GB tablet swapping hard after a low-memory kill that took longer than Android's service and broadcast timeouts: the service start commands and the `LOCK_TASK_ENTERING` broadcast queued behind it ended in ANRs, Android killed the new process too, and every relaunch repeated it. The gate waits for the Activity to be started, because a stopped one lays nothing out and the WebView would otherwise appear at the next start without a check. It then waits for the work with a deadline that the launch queued (`LaunchWork`, at most 10 seconds): both services must have run a start command carrying this launch's token or a later one, so an earlier command still queued for them does not count; tokens follow the time since boot, so a start command Android delivers again after the previous process died mid-start never counts either, and, when the launch entered lock task mode, `AdminReceiver` must have handled the broadcast. Finally it waits while `MemoryPressure` reports the system short of memory, meaning the low-memory flag is set, or 1,000 or more pages a second came back from swap during at least the second before the check while less than 800 MB was available. The swap-in rate comes from `pswpin` in `/proc/vmstat`, or from `/sys/block/zram0/stat` where that file is closed to apps, as on Android 8 on EMUI. On the 3 GB tablet the low-memory flag stayed clear in all 5,026 journal samples over 18 days, including every low-memory kill, and the same held for a forced thrash, during which swap-ins ran at 9,000-25,000 pages a second. On a normal day the five-minute average stayed under 100 most of the time. Normal use can pass the swap-in limit too: waking the display moved about 35,000 pages a second briefly, and one night's burst averaged 5,375. Available memory tells these apart: every reading of 1,000 pages a second or more during a forced thrash came with at most 422 MB available, and every one without a thrash with at least 1,424 MB; the low-memory kills before the swap-in rate was recorded happened with 286-396 MB. Before the reboot that released the kernel's unreclaimable memory, available memory never passed 519 MB in 13 days, so a thrash in that state still holds the WebView back. Binder latency, main-thread lateness and the trim level did not separate the two states. It checks again after 2, 4, 8, 16 and then every 30 seconds, and creates the dashboard anyway after 3 minutes, a limit that a recreated Activity inherits and that starts over when a stopped Activity starts again. Until then the window stays black, with a short note once the wait for memory passes 15 seconds, and the idle timeout starts counting only once the dashboard exists. After a restart with the display off, this moves the first page from the night to the moment the display wakes, so the display shows black briefly rather than the previous content; the swapping that waking causes does not hold the page back while memory is plentiful. While no WebView exists yet, the watchdog neither counts a screen-off window nor defers a reload, so the new page is not reloaded right after it appears. A cold process also discards saved instance state, so fragments restored from the previous process cannot create their WebViews before the gate opens. Once a WebView exists, later Activities in the process, such as a recreation, skip the gate. The diagnostic journal records each wait and the opening with the memory readings and the time since the gate was created or, after a stop, its first check since then, notes once when no swap-in counter can be read, and memory samples include the swap-in rate since the previous sample.
3. `KioskService` connects to the configured broker, publishes Home Assistant discovery/state/availability, and converts MQTT or schedule requests into screen and brightness commands. `AlarmPingSender` keeps the broker session alive through display-off suspend, where Paho's default timer-based keep-alive would stall; Paho measures keep-alive time with `ElapsedRealtimeTimer`, which keeps counting through suspend.
4. Commands that require UI state are sent through package-scoped, non-exported broadcasts to `MainActivity`; Device Owner screen-off can be executed directly by the service.
5. The Activity reports resulting screen and brightness state back to the service, which publishes retained MQTT state. What a newly created Activity sees is reported as an observation only, because Android may recreate it while the display is dark, for example right after a maintenance restart. Hardware screen transitions are reported but never redefine the requested state: Android wakes the display on charger events, and a charge-maintaining smart plug must not be able to cancel the screen schedule. During a scheduled OFF window the service disables the stay-awake-while-plugged policy and restores screen-off after a charger event.
6. After inactivity, the Activity overlays a separately origin-restricted idle WebView. Its first touch is consumed, the profile for the current day and time is resolved again, and the underlying dashboard is revealed.
7. The watchdog broadcasts a health-check tick to the Activity, which checks the visible WebView's JavaScript health and probes each instantiated dashboard plus the active idle page off the main thread. `PageLoadGrace` counts a page that is still within the first 35 seconds of a load as neither healthy nor failed, so a tick that lands just after a page was created or reloaded does not restart that load; a main-frame error or a load that outlives the grace period still fails. The period starts with every load the app begins (creation, reload, retry) and with a navigation the page starts itself after a finished load, such as a `location.reload()` or a redirect to a login page; further redirects before a load finishes do not restart it. 35 seconds keeps the ticks after a health-check reload off the boundary for the 15-, 30- and 60-second intervals, whether the failure reloaded the page at the tick or after the 5-second JavaScript timeout, so whether a tick is skipped never depends on a few milliseconds of jitter. With the default 30-second interval exactly one tick after each reload is skipped; at 15 seconds two are, at 60 seconds none. At 10 and 20 seconds a timeout's reload can still put a tick on the boundary. The price is a slower escalation for a load that never finishes: with the default 30-second interval every reload costs one skipped tick, so the third failure, which recreates the Activity, comes about 2 minutes after the first instead of 1; with a 10-second interval each reload skips 3 ticks, or possibly 4 after the first failure if it was a timeout (a page that never loads fails later checks at once), and the restart takes about 80 to 90 seconds instead of about 20. Reachability history belongs to the fragment, view, configured URL, and content generation; a recovered host reloads only its affected page. Results for replaced or reloaded content are discarded. A retained hidden idle page keeps its unresolved outage until it is shown again, unless a maintenance reload restarts it in the meantime. During the non-Device-Owner black-overlay screen-off mode, host probing continues and recovery reloads wait for wake; hardware screen-off suspends probing. Probing also continues while settings covers the retained dashboard, with recovery reloads deferred until the dashboard Activity resumes.
8. Periodic maintenance, memory pressure, and long hardware screen-off windows use a general reload broadcast that restarts every dashboard page. The Activity hands it to `MaintenanceReloader`, where `IdleMaintenanceReload` keeps it off the idle page while that page is on screen: the reload is deferred until the idle screen is dismissed by a touch, by turning the screen off, or by the Activity pausing. After a touch it waits another 30 seconds, so the user's first moments on the dashboard do not compete with reloading the slideshow for network, CPU and renderer memory; the idle screen returning first keeps it deferred, and the screen turning off or the Activity pausing in the meantime runs it at once. Maintenance reloads therefore never replace playback with a blank page. Recovery paths still can: a failed JavaScript health check or a recovered host reloads the visible idle page, a lost renderer recreates the Activity, and the nightly restart in the next step may run during idle playback. The deferral itself has no time limit; the scheduled restart, or a scheduled tablet reboot, which also ends the process, bounds it to the shorter of their intervals for an idle page that stays on screen. With neither scheduled, or the tablet staying in use through the postponement window, the deferral stays unbounded until the idle screen is dismissed. A hidden idle page is reloaded immediately. Like any reload, this starts its reachability history afresh, so an outage recorded before it was hidden is not carried over.
9. Restarts are scheduled only by the owner, in the Memory section; they are off by default. When they are on, `ScheduleManager` raises the maintenance alarm once a day and `KioskService` skips it until the chosen interval (1, 2, 3 or 7 days) has passed since the process started, which also counts a restart Android forced. On a 3 GB Huawei tablet the Mali GPU driver keeps about 40 MB a day of native heap while an idle slideshow with a blurred backdrop plays, in an internal pool that only the end of the process releases; reloads leave it in place, and so do recreating the Activity with all its WebViews and destroying the render thread's EGL context. Only a new process starts from scratch, so as Device Owner Glance restarts its process: `AppRestarter` schedules an alarm that relaunches `MainActivity`, records a relaunch marker that the first `KioskService` start in the new process also acts on, and kills the process. The new Activity re-enters lock task mode and starts both services as on any launch. A restart keeps the persisted requested screen state instead of recomputing it from the schedule, so a manual MQTT ON inside the OFF window survives it. With a screen schedule the alarm fires 15 minutes after the scheduled screen-off (at most halfway through the OFF window), and the service restarts at once while the display is off. Without a schedule it fires at the configured quiet time. When the display is on, `KioskService` asks the Activity, because only it knows whether the tablet is in use: it restarts during idle playback or once 10 minutes have passed without a touch, a return to the dashboard, or the display waking. Otherwise the service asks again every 10 minutes, which also survives a settings save recreating the Activity, and gives up for the night after three hours. A restart with the display on turns it off first and back on from the new process, so the seconds without a dashboard are dark rather than showing the home screen. The dying process does not report that dark display, and the new one starts out reporting it on, so the `Screen` light stays ON; MQTT drops briefly, so Home Assistant sees the tablet unavailable. The service cancels the relaunch alarm once it has launched the dashboard itself. A process younger than an hour is not restarted. Without Device Owner, which an Activity start from the background needs from Android 10 on, the Activity reloads every page instead, including the idle page on screen, and reports completion; that refreshes the pages but does not release memory. Recovery builds (`BuildConfig.RESTORE_BUILD`) restore older app code without this restart and hide its settings in the remote panel.
   A restart does not help when the memory is the kernel's. On the same tablet `SUnreclaim` in `/proc/meminfo` reached 1.47 GB, over half of the RAM after 236 days of uptime, and the low-memory killer then closed Glance in the foreground although its own heap was stable. `KernelMemoryMonitor`, fed by the watchdog's 5-minute memory sample, stores the lowest reading of each hour since boot in its own preferences, so the history survives a restart of Glance; a changed `Settings.Global.BOOT_COUNT`, or failing that a stored hour later than the current uptime, starts it over. `KernelMemoryTrend` turns those minimums into a daily pace and the Memory section, on the tablet and in the panel, shows the current level, the pace, the device uptime and whether a tablet reboot is due: at 40% of the RAM, or when the pace reaches that level within 30 days. Recovery builds do not feed the monitor, and the panel says so instead of judging stale minimums.
   The owner can also schedule a tablet reboot there, once a week, every 2 weeks or every 30 days, counted from boot (`elapsedRealtime`), so a reboot by hand also counts. It is Device Owner only (`DevicePolicyManager.reboot`); without it the tablet's Memory section shows it disabled and the panel explains it instead of offering it, and a save leaves the stored choice alone. `ScheduleManager` raises the maintenance alarm while either a restart or a reboot is scheduled, and `NightlyMaintenancePolicy.action` decides each night: a due reboot replaces the restart, otherwise the restart runs on its own interval. The reboot follows the restart's path and conditions above, with the service rebooting at once while the display is off and the Activity deciding otherwise. `TabletRebooter` journals the reboot, asks the memory trend for a verdict like `AppRestarter`, commits a marker with the wall-clock time and `Settings.Global.BOOT_COUNT`, and reboots a second later. A refused reboot (`IllegalStateException` during a call, or any other runtime exception), or no `ACTION_SHUTDOWN` broadcast within three minutes, clears the marker and restarts the process instead. Once the shutdown is announced it is left to finish however long it takes, since a restart in the middle would drop the marker; on a tablet swapping hard, shutting down can take over a minute. While the reboot is pending the service does not report the display going dark. After the boot, `BootReceiver` launches the dashboard, which enters lock task mode and starts the services as after any boot. The first `KioskService` start consumes the marker; when it was written in the previous boot (a changed boot count, or, without one, less uptime than time since the marker) and at most 30 minutes ago, the service keeps the persisted requested screen state instead of applying the schedule and sends it through the usual light command: the display turns off again when that state is off, and a manual MQTT ON inside the OFF window stays on, with the `Screen` entity published accordingly. Any other boot applies the schedule as before.
10. An authenticated remote form save updates `AppConfig`, asks `KioskService` to rebuild MQTT and schedule state, and broadcasts the same UI reload used by local settings (`ACTION_RELOAD_UI`, which recreates the Activity; unlike the maintenance reload above, it is not deferred during idle playback).

## Security model

- Dashboard and broker endpoints are entirely user-configured. The app has no project-operated backend or telemetry.
- Top-level WebView navigation is origin restricted. Additional authentication origins require explicit configuration.
- MQTT credentials stay in private application storage; the password is encrypted at rest. WebView credentials and cookies remain under Android WebView's storage model.
- Remote configuration is disabled by default. When enabled, it uses bounded HTTP parsing, a limited worker pool, PIN retry lockout, expiring in-memory sessions, CSRF tokens, restrictive response headers, and never renders the stored MQTT password.
- Android backups are disabled. Receivers, services, and settings are not exported unless Android requires an exported entry point with a platform permission.
- Device Owner, signing keys, settings PINs, dashboard sessions, and broker credentials are trust anchors and must be protected operationally.
- Self-hosted updates are disabled by default and have no built-in URL. An update is installed only when its versionCode increases, its published digest matches, and it is signed by the certificate of the running installation, so the update transport is not a trust anchor.
- Cleartext dashboard HTTP, remote configuration HTTP, and MQTT are supported for local deployments, so transport confidentiality depends on endpoint configuration and network trust. Remote settings should be enabled only on a trusted LAN.

## Lifecycle and provisioning constraints

Device Owner provisioning gives Glance powerful kiosk controls and may require a factory reset. Updates must retain both the Android application ID and signing certificate. Forks should choose their own application ID and signing strategy before provisioning the first device.

That constraint decides how the project publishes. Releases carry an **unsigned** APK and always will: because an installed Device Owner accepts an update only from the certificate it was provisioned with, a signed release would bind every installation to one key held by this project, and losing or rotating that key would require a factory reset on every device using it. Each operator therefore signs with their own key, which also means the project holds no key whose compromise would reach an installed device. [Self-hosted updates](self-hosted-updates.md) describes the signing and distribution path built on this.

Vendor battery management can still interfere with long-running services. Deployment testing should cover boot, screen transitions, network loss and recovery, WebView updates, clock changes, and application updates on the target hardware.
